## 1. 参赛资格与队伍

1. 面向全球个人与团队开放。每人一个账号。
2. 队伍 1–3 人。每人只能属于一个队伍。提交以队伍名义进行。
3. 主办方、评测平台维护者及其直接合作者不参与评奖；其队伍在榜单上标记为隐藏。
4. 队名与内容须遵守行为准则（第 8 节）。

## 2. 赛程

所有选手使用同一个「参赛」入口，平台自动选择当前比赛。

| 阶段 | 时间（UTC+8） | 说明 |
|---|---|---|
| 比赛 | 10 月 5 日 00:00 – 10 月 7 日 23:59 | 提交项目，在三个正式场景 A、B、C 上评测；线上榜实时更新；选定最终版本 |
| 隐藏场景决赛评测 | 10 月 7 日 23:59 之后 | 主办方在一个隐藏场景上对每队的最终版本评测一次 |
| 核验与公布 | 隐藏评测之后 | 主办方核验前列队伍后公布最终排名（只看隐藏场景成绩） |
| 颁奖日 | 10 月 17 日 | GOSIM 深圳 |

## 3. 提交内容

1. 提交完整项目的公开 GitHub 仓库链接或不超过 50 MB 的私有 ZIP，项目语言不限。平台检查后，由你审阅并确认固定的源码版本、启动设置和提出的适配文件。
2. 正式比赛仅接受完整项目，不接受 CSV 文件或本地 CSV 会话。
3. 评测逐轮提供当前观测，服务器先记录本轮决策，再提供下一轮数据。未来天气和隐藏异常答案保密。
4. 所有队伍的每日评测额度相同，以页面显示为准，按 UTC 0 点重置；额度内可自由评测。每批包含全部三个正式场景（A、B、C）。因平台原因失败的批次不计入额度；项目自身构建失败、崩溃或输出不符合协议导致的失败照常计入。
5. **最终版本。** 比赛期间，队伍任一成员都可以在「参赛」页面把本队一个已确认（且未撤回）的版本标记为**最终版本**，并可在比赛结束（10 月 7 日 23:59，UTC+8）前随时更改或取消；比赛结束后锁定。若始终未选择，默认使用本队在线上榜上最高分那次评测的版本。已选为最终版本的版本不能撤回。

## 4. 运行与模型 API

1. Python 是平台运行器，不限制项目语言。平台在指定容器中运行已确认的版本。
2. 模型调用可选，由选手自备 API 和额度，平台不提供模型额度。服务商不限，接口需兼容 OpenAI，地址需是公网可访问的 https 地址（默认 443 端口），不接受 IP 地址或内网地址。密钥通过 HTTPS 提交，不写入项目、运行记录或日志。不要将密钥放入项目源码。密钥的处理方式由选手自选：
   - **不保存（默认）**：密钥只留在你打开的「参赛」页面里，服务器不保存。每次评测都必须保持该页面打开，直到评测结束；页面关闭期间的模型调用会失败。**比赛结束后的隐藏场景决赛评测期间（时间由主办方通知）也必须打开页面；如果你的队伍进入前列、需要做复现核验，核验时同样需要按约定时间打开页面配合。**
   - **加密保存（需主动选择）**：密钥加密保存在服务器上，只在评测和核验时使用，比赛结束、成绩核实后自动删除。评测时无需保持页面打开。
   选择可以随时更改；从「加密保存」改为「不保存」时，服务器上的密钥立即删除。
3. 允许使用外部算力和外部服务，包括自备的模型 API 和自有服务器。平台容器（2 核 CPU、2 GB 内存）的限制只约束在平台上运行的部分。
4. 每一轮决策必须由程序自动做出，禁止人工参与或代为决策。
5. 试图读取其他队伍数据、篡改评分或故意耗尽平台资源，可以导致取消资格。

使用模型时，在「参赛」页填写支持 HTTPS 的接口、模型和密钥，并选择「加密保存」或「不保存」（见第 2 条）。已保存的密钥可以随时更换或删除。

## 5. 评分

得分由公开的 `scoring_core.py`（schema `challenge-score-v3`）按 `config/score_config.json` 中的常数计算。概要：

1. 时间是真实夜晚上的 900 秒时隙日历。`observe` 从游标起持续天区的 `nominal_exptime_seconds`，可跨时隙并切分为分段；`wait` 消耗当前时隙剩余时间。
2. 对**完成**曝光的每个分段，在分段中点：
   `A = min(instrument_efficiency · transparency · sky_quality / (seeing_arcsec · airmass), 3.0)`，`combined = A · lunar_quality_factor`，
   `base = V_tile · (segment_seconds / nominal_exptime_seconds) · combined`，其中 `V_tile` 为天区目标的 `science_weight` 之和；
   `bonus = base · B[program]`，`B = {DARK 0.25, BRIGHT 0.15, BACKUP 0.08}`，仅当决策项目等于 `combined` 所对应的区间（DARK ≥ 0.65，BRIGHT ≥ 0.40，否则 BACKUP）时支付。
3. `total = base_science + program_bonus + request_reward + report_reward + coverage_bonus − unsafe_observation − invalid_action − avoidable_wait − required_miss − flexible_shortfall − request_miss − fault_misreport − wrong_tag_report`：每次不安全观测（圆顶关闭时观测）2000；每次无效动作（未知天区/时隙/项目、窗口之外、错误请求标注、在天区落下或夜晚结束前无法完成的曝光、过期决策）100；每秒可避免等待 0.001；每块未完成的必做天区（REQUIRED）1000；每个分区的可选天区（FLEXIBLE）不足 4 块的，每缺一块 100；到期请求每个所需天区 190（完成则每个所需天区奖励 140）。
4. **覆盖均匀性**（`coverage_bonus`）：`coverage_bonus = W · base_science · E`，其中 `E` 是已完成天区在各分区间分布的均匀度（Jain 公平指数：`(Σx)² / (n·Σx²)`，八个分区拍得一样多时为 1，全挤在一个分区时为 1/8）。权重 `W` 写在每个场景的 `config/score_config.json` 里：**当前比赛场景为 0.35**。广域巡天要靠均匀覆盖才能支撑统计，所以把天区都集中在好拍的那几个分区会付出代价。
5. **重复观测与异常上报**：重复观测合法——每个天区按历次观测的最高分入账（更差的重复不拉低它），完成状态仍以首次合法观测为准。场景里有隐藏的 per-tile 标签（nova ×1.5、reddening ×0.8，静默作用于评分）和区域级仪器故障（效率骤降、不进预报）。`decision_response` 可附 `reports` 数组上报异常：标签在终局按每 (tile, 标签) 首次上报结算，对 +100、错 −150；故障上报正确则一天后发布故障状态、两天后修复，误报在每次正确上报之间有一次免费额度、之后每次 −100。标签赏罚与故障参数见 `score_config.json` 的 `reporting` / `anomaly_tags` / `fault_response` 小节。

6. 只有完成的曝光计分。被关闭天气中断的曝光不计分也不受罚；被几何或夜晚结束中断的曝光不计分并记为无效动作。
7. 终局惩罚适用于每次运行，包括被时钟或智能体错误截断的运行。可行机会少于所需天区数的到期请求予以免责。
8. 完成度（已完成天区 ÷ 天区数）与各分区可选天区缺额显示在榜单上；它们通过终局惩罚进入得分。
9. 正式赛每批评测覆盖全部正式场景，批次成绩为该批所有场景分数的算术平均；全部场景完成后才进入线上榜，榜单取每队最高分的完整批次，不能拼接不同批次的场景最高分。
10. **固定场景与逐轮提交。** 三个正式场景 A、B、C 固定，且对所有队伍相同：每队每次评测都使用同样的场景，不按队伍随机生成。场景文件、天气、预报和事件不公开，评测时逐步提供观测。平台先记录本轮决策，再提供下一轮数据；不能预先提交未来轮次或替换已经接受的决策。未来天气和隐藏异常答案保密。本队每次评测的结果 ZIP 仍可下载。
11. **隐藏决赛场景。** 比赛结束后，主办方在一个选手从未见过的隐藏场景上，对每队的最终版本（第 3 节第 5 条）评测且只评测一次，不占每日额度。隐藏场景、逐步数据、运行日志和结果在主办方公布最终成绩前保密。最终排名只看这个隐藏场景的成绩，线上榜不决定最终排名。

## 6. 排名、同分与核验

1. **最终排名**：只计各队最终版本在隐藏场景上的成绩（第 5 节第 11 条），按得分降序排名。隐藏成绩严格同分的处理由主办方决定，并随成绩一起公布。
2. **线上榜**：比赛期间实时显示各队最高分批次（第 5 节第 9 条）；严格同分时先完成评测的批次在前。它只用于反馈，不决定奖项。主办方可在最后几小时封榜。
3. 选择「不保存」密钥的队伍（第 4 节第 2 条），须在主办方通知的隐藏场景决赛评测期间保持「参赛」页面打开，否则模型调用会失败。
4. 确认奖项前，主办方会对前列队伍做复现核验：可重新运行其最终版本，并可要求提供完整代码、所用外部服务与模型的版本和配置、评测期间的调用记录。核验结束前，请保持所用外部服务和已保存的密钥可用；选择「不保存」密钥的队伍，须在核验时按约定时间打开「参赛」页面配合。无法运行、表现与上榜成绩明显不符或发现人工干预的，结果将被移除。
5. 若发现评分器缺陷，主办方可重新评分。评分器或常数的任何变更都会带版本号公告，并适用于该阶段全部提交。线上比赛开始前，当前常数为主办方的临时校准值。
